# controlador-tests — Design Specification (v1)

This document specifies the first version of **controlador-tests**, a private, offline practice-test
app for the iPhone that lets the user take timed multiple-choice tests for the ENAIRE air traffic
controller exam (Temario first, English later) without having to open a Claude session each time.
It covers the goal and constraints, the architecture, every screen, the exact data formats that
travel between the phone and the Mac, how syncing works without any cloud service, how errors are
handled, how everything is tested, and what "done" means for v1. It was produced through a
brainstorming session on 2026-10-13 in which each section below was approved by the user before
being written down.

## 1. Purpose and context

### 1.1 The problem

Today, practising for the Temario (general knowledge) and English sections of the ENAIRE exam
requires a Claude session: Claude generates a synthetic test as a Markdown file, the user takes it on
paper or on screen while timing themselves by hand, writes their answers and doubt marks into a
"ficha" (a registration sheet), and then `registrar.py` writes the result into the master Excel
workbook. The bottleneck is the first step and the manual bookkeeping. The user wants to practise
much more often, from the phone, at any moment, and only come back to the laptop periodically to
sync.

### 1.2 The existing study system this app plugs into

The app does not replace the existing system; it becomes a new front end for it. The relevant parts
of that system are:

- **Test material** lives in `~/Documents/controlador/Primer Examen/Temario/Tests/`. Synthetic tests
  (generated by Claude) live in `Tests/SINTETICOS/` as `SYN-*.md` files. Each one has three parts: a
  `## TEST` section with the questions, a `## CLAVE` section with the answer key, and a
  `## SOLUCIONES RAZONADAS` section where every question is repeated with its answer, a citation of
  the exact page of the syllabus (for example `[T4, pág. 42]`), a difficulty level (N1 recognition,
  N2 comprehension, N3 fine discrimination), an explanation of why each wrong option is wrong, and
  often a memory hook ("Gancho").
- **The registry** lives in the Obsidian vault at `~/Documents/TheMind/ATC/teoria/`. Answer keys are
  archived in `20-REGISTRO/claves/[ID].txt` and fichas in `20-REGISTRO/fichas/[ID].md`.
- **A ficha** is a Markdown file whose header is a list of `campo: valor` lines (field: value):
  `id`, `categoria`, `dificultad`, `modo`, `intento`, `fecha`, `preguntas`, `limite`, `tiempo`,
  `tramos`, `respuestas`, `clave`, `dudas`, `atascos`, `subtipos`, `causas`, `sintetico`,
  `observaciones`, and a few others. The complete list of accepted fields is `CAMPOS_INTAKE` in
  `99-SCRIPTS/registrar.py`; any field not in that list makes the script refuse the ficha.
- **`registrar.py --intake <ficha>`** reads a ficha and writes one row per test and one row per
  question into `Temario/Teoria_Maestro_v1.xlsx`.
- **Methodological rules** that the app must respect: synthetic tests "train, they do not measure",
  so they are registered with `sintetico: si` (Intento 9) and excluded from all progress series;
  second and later attempts on the same test are excluded from the series because a repeated test
  measures recognition memory rather than knowledge; and the exam scoring is +1 per correct answer,
  −0.33 per wrong answer, 0 per blank, with a pass mark of 25/50 and roughly 60 seconds per question.

### 1.3 Success criteria

The app is successful if the user can take far more tests than today, from the phone, and every
attempt reaches the Excel workbook with **better data than the manual process**: exact total time,
per-question time, doubt and "stuck" marks recorded at the moment they happen, and failure causes
tagged by the user rather than deduced afterwards. Several existing fichas carry notes such as
"SIN TIEMPO" (no time recorded) or "the doubt was noted without a letter, so it is registered as
blank"; the app makes those situations impossible.

### 1.4 Constraints

- **Devices:** iPhone 16 and MacBook Air M4 running macOS Sequoia 15.5.
- **No paid Apple Developer account.** A native app signed with a free account stops launching after
  7 days until it is re-signed from Xcode.
- **No iCloud.** The user does not use or pay for iCloud.
- **No running costs and no always-on server.**
- **Privacy:** the question bank contains material derived from copyrighted academy syllabi, and the
  results are personal. Neither may ever be published.
- **The existing backend must not change in v1:** `registrar.py`, the ficha format and the Excel
  workbook stay exactly as they are.
- **Tooling preferences:** Python tools use `uv`, Ruff and pytest; test-driven development is
  mandatory for logic-heavy Python and TypeScript modules.

## 2. Decisions taken and why

### 2.1 A Progressive Web App instead of a native app

A **Progressive Web App (PWA)** is a website that can be added to the iPhone home screen, where it
opens full-screen like a normal app, works without an internet connection, and stores data locally on
the phone. It works offline thanks to a **service worker**, a small script the browser keeps on the
device that intercepts network requests and answers them from a local cache.

The alternative, a native SwiftUI app, was rejected because without a paid developer account it must
be re-signed every 7 days. A paid account ($99/year) would remove that problem but adds cost for no
functional gain at this scale. The tradeoff accepted with the PWA is that iOS gives web apps slightly
weaker storage guarantees than native apps (see [6.3](#63-storage-on-the-phone)) and no native
file-system access, which is why syncing goes through file import and the share sheet.

### 2.2 AirDrop instead of iCloud or a server

Data moves between phone and Mac as two small JSON files sent over **AirDrop**, Apple's local
peer-to-peer file transfer. It needs no account, no cloud storage and no internet, and since both
devices use the same Apple ID, transfers are accepted without a prompt.

- `bank.json` goes **Mac → phone**: the question bank.
- `results.json` goes **phone → Mac**: every attempt the user has made.

Alternatives considered: iCloud Drive (rejected because the user does not use iCloud, although the
free 5 GB would have been more than enough for files of a few megabytes); a local HTTP server on the
Mac that the phone fetches from (rejected because an HTTPS page cannot fetch from a plain-HTTP local
address, and fixing that requires installing custom certificates on the phone); a hosted backend
(rejected for cost and privacy). The tradeoff is that syncing is manual — two taps each way — which
matches the user's own idea of "connecting the phone and the laptop whenever needed".

### 2.3 Fixed tests and random practice, both

- **Fixed tests** are the tests Claude generates (for example `SYN-T12-001`). Each has one ID and one
  answer key, so the app runs it exactly as written and the result is registered in the Excel like
  any other test.
- **Random practice** lets the user pick chapters and a question count; the app draws questions at
  random from every question in the bank. It gives unlimited combinations from existing material.

Because random draws reuse questions the user may have already seen, they measure recognition as
much as knowledge. They are therefore always registered as synthetic (`sintetico: si`, Intento 9)
so they never pollute the progress series. The same random-draw mechanism will later power the
error-practice mode (see [9. Future work](#9-future-work)).

### 2.4 Synthetic tests first, academy tests later

v1 ships with the 9 synthetic Temario tests only. They are already structured Markdown with keys and
reasoned solutions, so conversion is mechanical and verifiable. The 16 academy and official tests
that have answer keys exist only as PDFs whose solutions are a bare letter; extracting and checking
roughly 500 questions is a separate content task. The bank format keeps `explanation`, `cite` and
`hook` optional precisely so those tests can be added later with no app change.

### 2.5 Exam mode and Practice mode chosen per test

Before every test the user chooses:

- **Exam mode:** a hard stop. At 0:00 the test ends and every unanswered question counts as blank.
  This trains pacing under real conditions.
- **Practice mode:** a soft limit. The timer turns red and keeps counting past the limit, and pausing
  is allowed. This measures what the user knows when time is not the constraint.

The chosen mode is stored with every attempt so results from the two conditions are never confused.
**Implementation note:** the ficha field `modo` cannot carry this, because `registrar.py` only
accepts `Bloque` (single chapter) or `Mixto` (several chapters) there, and unknown fields are
rejected. In v1 the mode is written into `observaciones`, for example
`Modo examen (corte duro). Hecho en la app.` A dedicated field can be added to `registrar.py` later
if the user wants to filter by it in the Excel.

### 2.6 Hosting on GitHub Pages from a public repository

A PWA can only be installed from an HTTPS address. **GitHub Pages** serves static files from a GitHub
repository over HTTPS for free. On the free plan the repository must be public, which is acceptable
because the repository contains **only application code**: no questions, no results, no syllabus
text. The question bank reaches the phone exclusively via AirDrop. A safety test (see
[7.3](#73-repository-safety-test)) blocks any bank or result file from ever being committed.

**Account note:** on this Mac the GitHub CLI (`gh`) is currently logged in only to the employer's
GitHub Enterprise server. This personal project must never be pushed there.
Before deployment the user runs `gh auth login --hostname github.com` with their personal account,
and every `gh` and `git remote` command for this project names `github.com` explicitly.

### 2.7 Technology stack

| Layer | Choice | Why |
|---|---|---|
| App language | TypeScript | Static types catch data-format mistakes between bank, attempts and export |
| UI | Preact | A 3 KB implementation of the React model; small, fast on a phone, familiar API |
| Build | Vite | Produces a plain static folder suitable for GitHub Pages; fast dev server |
| Offline | `vite-plugin-pwa` (Workbox) | Generates the service worker and the web app manifest |
| Phone storage | IndexedDB via the `idb` wrapper | The browser's built-in database; holds far more than `localStorage` and survives restarts |
| App tests | Vitest + `@testing-library/preact` | Fast unit tests for pure logic and a few screen-flow tests |
| Mac tools | Python 3.12+, `uv`, Ruff, pytest | Matches `registrar.py` and the user's standard toolchain |

Two alternatives were rejected: a single hand-written HTML file (no build step, but hard to test and
modularise, and it would grow into one very large file) and SvelteKit (pleasant, but a new framework
with no benefit at this size).

## 3. Architecture

### 3.1 The two halves and the loop between them

```
 Mac                                                    iPhone (PWA)
 ───                                                    ────────────
 SYN-*.md  ┐
 claves/   ├─► tools/build_bank.py ──► bank.json ──AirDrop──► Import bank
 fichas/   ┘                                                   │
                                                               ▼
                                                       Take tests (offline)
                                                               │
 Excel ◄── registrar.py ◄── fichas ◄── tools/import_results.py ◄──AirDrop── results.json
```

The Mac side owns the truth about questions (the Markdown files) and the truth about history (the
Excel workbook). The phone holds a copy of the bank and the complete history of attempts made on it.

### 3.2 Repository layout

The repository lives at `~/Documents/controlador/Primer Examen/controlador-tests/`.

```
controlador-tests/
├── app/                      Preact + TypeScript PWA
│   ├── src/
│   │   ├── domain/           Pure logic, no UI: scoring, sampler, timer, attempts, bank
│   │   ├── storage/          IndexedDB access
│   │   ├── sync/             Bank import and results export
│   │   └── ui/               Screens and components
│   ├── tests/
│   └── vite.config.ts
├── tools/                    Python, managed with uv
│   ├── build_bank.py
│   ├── import_results.py
│   ├── tests/
│   │   └── fixtures/         Small hand-written test files, never real bank content
│   └── pyproject.toml
├── docs/superpowers/specs/   This document
└── .github/workflows/        Build and deploy to GitHub Pages
```

### 3.3 Folders outside the repository

Generated and personal files are written **outside** the repository so they can never be committed:

| Path | Contents |
|---|---|
| `Primer Examen/app-sync/bank.json` | The latest bank, ready to AirDrop |
| `Primer Examen/app-sync/results/` | An archived copy of every imported `results.json`, timestamped |
| `Primer Examen/app-sync/imported.json` | The ledger: the IDs of every attempt already registered |

`import_results.py` looks for the newest `results*.json` in `~/Downloads` (where AirDrop puts files),
or takes an explicit path.

### 3.4 App modules

Each module has one job and can be understood and tested without the others.

| Module | Responsibility | Depends on |
|---|---|---|
| `domain/scoring` | Correct/wrong/blank counts, net score, pass reference | nothing |
| `domain/sampler` | Builds random tests from chosen chapters and a count | nothing (takes a random seed) |
| `domain/timer` | Elapsed time from wall-clock timestamps, hard stop, overtime, pause | nothing (takes a clock) |
| `domain/attempts` | Creating attempts, numbering them per test, resuming, closing | `scoring` |
| `domain/bank` | Validating a bank file and producing a human-readable summary | nothing |
| `storage/db` | Reading and writing the bank and attempts in IndexedDB | `idb` |
| `sync/importBank`, `sync/exportResults` | File picker in, share sheet out | `domain/bank`, `storage/db` |
| `ui/*` | Screens | everything above |

The `domain/` modules never touch the clock, the random generator or storage directly; those are
passed in. That is what makes them deterministic and testable.

## 4. Screens and user flow

### 4.1 Home

- All interface text is in **Spanish**, matching the questions, the causes vocabulary and the rest
  of the study system.
- A switch between **Temario** and **English**. English is empty in v1, but the app treats subjects
  generically so English needs only content.
- The fixed tests, grouped by scope (T1, T2, T12…). Each row shows its status: not started, or the
  date, net score and number of attempts.
- A **Random practice** button.
- At the bottom: **Import bank** and **Export results (n pending)**, where *pending* means attempts
  never exported.
- A banner when an attempt has been unexported for more than 7 days (see
  [6.3](#63-storage-on-the-phone)).

### 4.2 Test setup

- The user chooses **Exam** or **Practice** mode. The time limit is shown: the test's `limit_min`, or
  1 minute per question for random tests.
- For random practice the user also ticks chapters and picks a question count. The count cannot
  exceed the number of available questions in the chosen chapters.
- On a fixed test already taken, a warning reads *"Attempt 2 — won't count in your series."*

### 4.3 Taking the test

- One question per screen with options a–d. Tapping an option selects it; tapping the selected option
  again clears it, leaving the question blank.
- Two toggles on every question: **Doubt** (maps to the ficha's `dudas`) and **Stuck** (maps to
  `atascos`).
- The timer at the top. In Practice mode it turns red once past the limit; a pause button is
  available.
- A grid of question numbers opens on demand; it shows answered, blank and flagged questions and lets
  the user jump to any of them.
- Time on screen is accumulated per question. The `tramos` checkpoints are the elapsed times at
  which the 10th, 20th, 30th, 40th and 50th answer was given, counting answers in the order they were
  first given regardless of question number (up to five checkpoints, which is what `registrar.py`
  accepts).
- **Interruptions:** the attempt is saved after every action. If the app is closed — a phone call, a
  crash, the phone locking — reopening it resumes the attempt at the same question. The timer is
  computed from real timestamps, so in Exam mode time keeps running while the user is away, exactly
  as in a real exam; in Practice mode, closing the app counts as a pause.
- **Finish** asks for confirmation and states how many questions are blank.

### 4.4 Results and review

- **Summary:** correct, wrong and blank counts; net score (correct − 0.33 × wrong); the pass reference
  of the test; total time and the limit.
- **Review** with filters *All*, *Wrong*, *Blank* and *Doubt*. For each question: the stem, the
  user's answer, the correct answer, the explanation, the page citation and the memory hook.
- **Cause tagging:** on every wrong or doubted question the user can choose one cause from the closed
  vocabulary in `Temario/GUIA-REGISTRO.md`: *No conocía el dato*, *Confundí dos conceptos*, *Lo
  recordaba mal*, *Mala lectura del enunciado*, *Dudé entre dos opciones*, *Sin tiempo*, *Otro*.
  Tagging is optional and can be done or changed at any time before export. Today these causes are
  deduced after the fact from the chosen wrong option; tagging them at review time is more reliable.

### 4.5 Out of scope for v1

Error-practice mode, statistics and charts, English content, academy and official tests, shuffling
of answer options, and editing questions on the phone.

## 5. Data formats

JSON (JavaScript Object Notation) is the text format used for both files. Both carry a `schema`
number so that a future app version can recognise and migrate older files.

### 5.1 bank.json

Produced on the Mac by `tools/build_bank.py`, consumed by the app.

```json
{
  "schema": 1,
  "built": "2026-10-13T18:00:00+02:00",
  "questions": [
    {
      "id": "SYN-T4-003#7",
      "subject": "temario",
      "tema": 4,
      "stem": "…",
      "options": { "a": "…", "b": "…", "c": "…", "d": "…" },
      "answer": "b",
      "level": "N2",
      "subtipo": "t4-declinacion-magnetica",
      "cite": "T4, pág. 15",
      "explanation": "…Markdown…",
      "hook": "…"
    }
  ],
  "tests": [
    {
      "id": "SYN-T4-003",
      "subject": "temario",
      "scope": "T4",
      "title": "Tema 4: Cartografía",
      "questions": ["SYN-T4-003#1", "SYN-T4-003#2"],
      "limit_min": 20,
      "pass_ref": 10,
      "synthetic": true
    }
  ]
}
```

Field rules:

- `id` of a question is `<test id>#<number>`, which is stable and readable.
- `tema` is the chapter number 1–9. Questions from a mixed test such as `SYN-T12-001` get their
  chapter from the prefix of their `subtipo` (`t1-…` or `t2-…`).
- `answer`, `options` keys and `level` are required. `subtipo`, `cite`, `explanation` and `hook` are
  optional in the format; for the 9 synthetic tests `build_bank.py` requires `answer`, `cite` and
  `explanation` and fails otherwise.
- `explanation` and `hook` are Markdown and are rendered on the review screen.
- `scope` follows the naming convention of `Temario/LEEME.md` (`T1`…`T9`, `T12`, `T78`, `FULL`).

### 5.2 results.json

Produced by the app, consumed on the Mac by `tools/import_results.py`.

```json
{
  "schema": 1,
  "exported": "2026-10-14T21:05:00+02:00",
  "attempts": [
    {
      "uuid": "6f1c…",
      "test_id": "SYN-T4-003",
      "kind": "fixed",
      "mode": "exam",
      "attempt": 1,
      "started": "2026-10-14T20:30:00+02:00",
      "finished": "2026-10-14T20:47:12+02:00",
      "limit_min": 20,
      "total_secs": 1032,
      "status": "finished",
      "items": [
        {
          "q": "SYN-T4-003#1",
          "key": "c",
          "ans": "c",
          "doubt": false,
          "stuck": false,
          "secs": 41,
          "first_answered_at_secs": 41,
          "cause": null
        }
      ]
    }
  ]
}
```

Field rules:

- `uuid` uniquely identifies the attempt; it is what the Mac ledger records.
- `kind` is `fixed` or `random`. Random attempts get a `test_id` such as
  `RND-T34-20261014-203015` (chapters drawn, then date and time to the second, so two random tests
  started in the same minute never share an ID) and list their questions in `items`, in the order
  presented.
- `attempt` is 1 for the first attempt on a fixed test, 2 for the second, and so on. Random attempts
  are always 1.
- `key` stores the correct letter **at the time of the attempt**. If a later bank corrects a question,
  the attempt remains self-contained and still scores and reviews correctly.
- `ans` is a letter or `null` for blank. `secs` is time spent on screen on that question;
  `first_answered_at_secs` is the attempt's elapsed time when it was first answered, used for
  `tramos`.
- Only attempts with `status: finished` are exported; an attempt in progress is never exported.
- Inside the app, each attempt additionally keeps a snapshot of its questions (stem, options,
  explanation, citation, hook) and its pass reference. These app-only fields are not exported. They
  are what keeps an old attempt fully reviewable after a later bank changes or removes a question.
- **Every export contains every finished attempt ever made.** The Mac skips the ones it already
  registered. This means a lost or failed AirDrop never loses data and the user never has to track
  what was already sent.

### 5.3 How build_bank.py reads the synthetic tests

Inputs: every `Temario/Tests/SINTETICOS/SYN-*.md`, the matching `20-REGISTRO/claves/[ID].txt` and,
when present, `20-REGISTRO/fichas/[ID].md` for the subtipos.

- **Questions** come from the `## TEST` section: `**N.** stem` followed by four `a) … d) …` lines.
- **The key** comes from the `## CLAVE` section, which exists in two layouts: grouped uppercase
  (`BCACB DDDCA …`) in `SYN-T1-001`, and numbered lowercase rows (`1-10   c a b d c   b c b d b`) in
  the later tests. Both are parsed.
- **Solutions** come from `## SOLUCIONES RAZONADAS`, which also exists in two layouts: the legacy
  `**1. b) 1944** · [T1, pág. 5] · N1` in `SYN-T1-001`, and
  `**Respuesta: c) …** · [T4, pág. 6] · N1` under a repeated stem in all later tests. From each
  solution block the tool takes the cited page, the level, the explanation text and, if present, the
  paragraph starting with `**Gancho:**` as the hook.
- **Cross-checks, any of which aborts the build with a message naming the file and question:**
  the `## CLAVE` section disagrees with `claves/[ID].txt`; the answer letter in a solution disagrees
  with the key; a question has fewer or more than four options; the number of questions differs
  between sections; a required field is missing.
- Header fields (`id`, `alcance`, `preguntas`, `tiempo`, `aprobado_referencia`) come from the YAML
  front matter (the `---` block at the top). For older files without front matter, the scope is taken
  from the file name and the limit defaults to 1 minute per question and the pass reference to half
  the questions.
- Output: `Primer Examen/app-sync/bank.json`, plus a printed summary of tests and questions per
  chapter.

### 5.4 How import_results.py writes fichas

For every finished attempt whose `uuid` is not in `app-sync/imported.json`:

1. **Choose the ficha file.** If `20-REGISTRO/fichas/[test_id].md` exists and its `respuestas` field
   is empty (Claude prepares fichas in advance with key and subtipos), fill that file in, preserving
   its body text. Otherwise create a new one; for second and later attempts the name is
   `[test_id]-i[attempt].md`, for example `SYN-T4-001-i2.md`.

   **Why the ID itself carries the suffix (amendment of 2026-10-13):** `registrar.py` forces
   `intento = 9` for every synthetic test and refuses a row whose `id` and `intento` already exist
   in the workbook. A second attempt at `SYN-T4-001` registered under the same `id` would therefore
   always be rejected as a duplicate. Giving repeat attempts the `id` `SYN-T4-001-i2` keeps
   `registrar.py` unchanged and keeps every attempt registrable.
2. **Fill the fields**, all in the existing format:

   | Field | Value |
   |---|---|
   | `id` | `test_id` for the first attempt; `test_id-i[attempt]` for later ones |
   | `categoria` | `SYN` for synthetic and random tests |
   | `dificultad` | `SINTETICO` |
   | `modo` | `Bloque` if one chapter, `Mixto` if several |
   | `intento` | `attempt` |
   | `fecha` | date of `started` |
   | `preguntas` | number of items |
   | `limite`, `tiempo` | `limit_min`; `total_secs` as `mm:ss` |
   | `tramos` | elapsed times at the 10th, 20th, 30th, 40th and 50th answer given (from `first_answered_at_secs`), as `mm:ss`, up to five |
   | `respuestas`, `clave` | uppercase letters grouped in tens, `-` for blank |
   | `dudas`, `atascos` | question numbers, comma-separated |
   | `subtipos` | from the prepared ficha if present, otherwise from the bank's `subtipo` per question |
   | `causas` | `n: Cause` groups separated by `;` |
   | `sintetico` | `si` |
   | `observaciones` | mode, start and end time, and "Hecho en la app" |

3. **Show a summary** of every ficha about to be registered and ask for confirmation.
4. **Run** `uv run --with openpyxl python 99-SCRIPTS/registrar.py --intake <ficha>` for each one, in
   chronological order.
5. **Record** the attempt's `uuid` in the ledger only after `registrar.py` exits successfully, then
   archive the `results.json` into `app-sync/results/`.

## 6. Sync, storage and error handling

### 6.1 Importing a bank on the phone

"Import bank" opens the iOS Files picker; the user chooses the AirDropped `bank.json` (AirDrop saves
it in Files › Downloads). The app validates the schema number and the structure, then shows a summary
before replacing anything, for example *"New bank of 13/10: 10 tests, 200 questions (+1 test since
08/10). Replace?"*. An invalid file produces a readable message naming the problem and **the previous
bank stays untouched**. Importing a bank never modifies or deletes attempts.

### 6.2 Exporting results from the phone

"Export results" builds `results-YYYYMMDD-HHMM.json` and opens the iOS share sheet through the Web
Share API (`navigator.share` with a file), from which AirDrop is one tap. If sharing is unavailable or
fails, the app falls back to a download, which saves the file into Files. Each export records the
time of the last export, used for the reminder below.

### 6.3 Storage on the phone

All data lives in IndexedDB. At first launch the app calls `navigator.storage.persist()`, which asks
iOS to treat its data as persistent. Web apps added to the home screen are exempt from Safari's rule
that deletes website data after 7 days without use. Two risks remain: iOS may still evict data under
severe storage pressure, and deleting the app from the home screen deletes its data. Both are
mitigated by design: the Mac and the Excel are the master copy, and the only data at risk is attempts
not yet exported. The home screen therefore shows a banner — *"3 attempts not exported — export
now"* — whenever any finished attempt is older than 7 days and has never been included in an export.

### 6.4 App updates

When a new version is pushed to GitHub Pages, the service worker downloads it in the background the
next time the app opens with a connection, and the app shows *"Update ready — reload"*. The prompt is
never shown during a test, and the update never applies until the user accepts it, so an attempt in
progress can never be interrupted by a reload.

### 6.5 Error handling on the Mac

- `build_bank.py` aborts on the first inconsistency with a message naming the file and the question.
  A bank with a wrong key can never reach the phone.
- `import_results.py` validates the results file before doing anything. If `registrar.py` fails on an
  attempt — the Excel is open in another program, a ficha is rejected — the tool stops, reports which
  attempt failed and why, and does not mark it as imported. The next run retries it. Attempts already
  registered in the same run stay registered and recorded in the ledger.
- Nothing is ever deleted from the phone by the Mac. The phone keeps the complete history.

## 7. Testing strategy

Test-driven development (writing the failing test first, then the code that makes it pass) applies to
every module listed under `domain/`, `sync/` and `tools/`.

### 7.1 App tests

Run with Vitest.

- **`scoring`:** net score with −0.33; counts of correct, wrong and blank; all-blank and all-correct
  edge cases; the pass reference.
- **`sampler`:** only questions from the chosen chapters; no duplicates; the count is respected and
  capped by availability; the same seed gives the same test.
- **`timer`:** elapsed time from timestamps; the hard stop at the limit in Exam mode; overtime and
  pause in Practice mode; correct elapsed time after the app was closed and reopened mid-test.
- **`attempts`:** numbering of attempts per fixed test; resuming an attempt in progress; unfinished
  attempts are excluded from export; export contains every finished attempt; `key` is captured at
  attempt time.
- **`bank`:** a valid bank is accepted with a correct summary; each kind of malformed bank is
  rejected with a readable message; a rejected import leaves the old bank in place.
- **Screen flow:** a few component tests for start → answer → mark doubt → finish → review → tag
  cause.

### 7.2 Mac tool tests

Run with pytest; code checked with Ruff.

- **`build_bank.py`:** each of the two key layouts and each of the two solution layouts parses
  correctly from small fixtures; every one of the 9 real synthetic tests builds without error (read
  from their real location, never copied into the repository); each cross-check failure aborts with
  the right message.
- **`import_results.py`:** a generated ficha matches, field by field, a known-good ficha written by
  hand from the current format; importing the same results file twice registers nothing the second
  time; a prepared ficha is filled in and its body preserved; a second attempt produces a `-i2` ficha;
  when `registrar.py` fails, the attempt is not added to the ledger.
- **Round trip:** build a bank from fixtures, simulate an attempt in the export format, import it,
  and run the real `registrar.py` against a **temporary copy** of the Excel workbook. The real
  workbook is never opened by any test.

### 7.3 Repository safety test

A test, also run in the GitHub Actions workflow, fails if any file named `bank*.json` or
`results*.json`, or any Markdown file containing a `## TEST` or `## CLAVE` section, is tracked by git.
The `.gitignore` excludes the same patterns.

### 7.4 Manual iPhone checklist

Performed once on the real device before v1 is declared done:

1. Install from the GitHub Pages address via Safari › Share › Add to Home Screen.
2. Import a bank via AirDrop and Files.
3. Enable airplane mode, close the app completely, reopen it, and take a full test.
4. Close the app mid-test in Exam mode, wait one minute, reopen: the test resumes and the minute has
   been counted.
5. Export results and AirDrop them to the Mac.
6. Push a new app version and confirm the update prompt appears on the home screen and never during
   a test.

## 10. Known risks

| Risk | Impact | Mitigation |
|---|---|---|
| iOS evicts the app's data | Unexported attempts lost | Persistent-storage request, 7-day export reminder, Mac as master copy |
| The user deletes the app from the home screen | Same as above | Same as above |
| A synthetic test file uses a third, unknown layout | Build fails | The build fails loudly, naming the file; the parser is extended with a fixture for the new layout |
| A bank with a wrong key reaches the phone | Wrong scores and wrong learning | Cross-check against `claves/*.txt` and against every solution's answer letter |
| Pushing to the employer's GitHub Enterprise by mistake | Personal project on a work server | Explicit `github.com` host in every command; check before the first push |
| Questions or results committed to the public repository | Copyrighted and personal data published | `.gitignore`, the safety test in 7.3, and all generated files written outside the repository |
